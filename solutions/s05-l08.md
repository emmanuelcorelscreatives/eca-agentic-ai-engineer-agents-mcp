# Worked solution: s05-l08

The current sequence is `record_lead(stable_call_id, ..., consent=True, opportunity=...)` → inspect the same durable outbox ID → separately `dispatch_once`. `ToolsService` owns this path; it does not repeat contact insertion when notification work is retried. Its stored initial receipt may still say pending, while the separate outbox row/dispatch receipt records the current notification outcome. Preserve both rather than rewriting history.

Default dispatch returns a local `dry_run`, never a real delivered claim. Local callback failure records `local_failed`; an explicit local-only retry can recover it. An explicitly permitted external adapter must return a genuine delivery receipt; uncertain outcomes remain held and cannot be automatically replayed. Record IDs, attempts and actual outcomes belong to the same durable ledger.

`workflow.contact_and_notify` is an introductory legacy comparison, not the durable authority. Its callback test alone does not prove an owner received anything. Current implementation and local mechanics are substantive, but genuine owner/sink notification remains unobserved. A concrete authorized course-only sink and actual observed receipt must be retained before teaching successful notification; no particular vendor or real personal mailbox is mandated by the PDF.
