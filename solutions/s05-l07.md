# Worked solution: s05-l07

`ToolsService.run` uses an explicit allowlist, a maximum of eight calls and one ordered result per submitted call ID. The valid lead and question persist; the unknown name returns a rejected result. Their durable call fingerprints and side effects share transactions in `storage.py`.

Reopen the same private SQLite file and resubmit the successful calls unchanged. The IDs and arguments recover their original stored receipts, so lead/question/outbox counts do not increase. A changed email, changed tool or otherwise substituted payload under an existing ID is refused. A nine-call list is rejected before any call is dispatched. Retention preserves a minimal dedupe tombstone so an expired action cannot silently recreate erased data.

These are the guarantees of the current `ToolsService` path, exercised in `tests/test_stage05_semantic_repairs_tools.py`. `twin.py/run_tools` remains a legacy comparison and must not be used to demonstrate durable resume. The current turn is explicitly synthetic/manual: actual model request origin and any future SDK bridge need their own retained observation before being claimed. No extra SDK bridge is a prerequisite for this registry-processing lesson itself.
