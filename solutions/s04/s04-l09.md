# Solution notes: s04-l09

Reference implementation: `TOOLS, execute_tool` in `examples/stages02-04/foundations.py`; optional SDK implementation in the adjacent `sdk_adapter.py`.

Only BOOK/PEN and the exact sku field are accepted. Tool schema declarations are not sufficient; execute_tool repeats the validation at runtime.

The full offline demo is reproducible with standard-library Python. The dedicated tests exercise success and negative boundaries; their PASS proves those code paths, not live model quality, named application installation or screenshot approval. Preserve this distinction in your submission.

Suggested discussion: Send {sku:BOOK}, unknown SKU, extra keys and malformed JSON. Add a new read-only lookup only after specifying allowed inputs, typed output, permission and bounded execution.

Reference path: `dispatch_contact` validates arguments and matching application consent, invokes the in-memory backend once, then returns a validated `ContactResult` or sanitized structured error. A successful repeat preserves one stored contact and stable ID. A malformed return after storage remains an unknown effect and cannot be retried automatically. The authored tests inspect both effect count and error types; they do not claim a real CRM/email action or that a model can authorize contact capture.
