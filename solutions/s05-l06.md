# Worked solution: s05-l06

The current authority is `ToolsService` in `projects/01-digital-twin/tools.py`, with transaction ownership in `storage.py`. A successful synthetic lead creates one `twin_leads` row, one `twin_calls` receipt and one structured `twin_outbox` entry. A successful saved question similarly creates one `twin_questions` row and its receipt/outbox. `Lead` and `Question` require literal explicit consent; invalid inputs fail before their writes. `ToolCall` binds name, arguments and a stable caller-supplied ID. Unknown names are not invoked.

For the lab's ordered manual batch, expect `ok`, `ok`, `rejected`. Inspect actual returned receipt IDs and the private database counts. The operation is a synthetic registry exercise, not an observed model-generated tool turn. The answering SDK agent has no write tools, and no extra SDK bridge is required to learn the typed registry itself.

`TOOL_SCHEMAS` documents the same input boundary for potential adapters; runtime dataclasses and transactions remain authoritative. The legacy `twin.py` examples are useful only as an introductory comparison and must not be credited with this durable action path. Relevant tests are `tests/test_stage05_semantic_repairs_tools.py`; a local pass proves its scoped mechanics, not model autonomy, notification delivery or production approval.
