# s05-l06: Build the Agent’s Tools

Create typed tools for recording leads, capturing questions and handling defined external actions.

## Authoritative implementation

Use `projects/01-digital-twin/tools.py` (`Lead`, `Question`, `ToolCall`, `TOOL_SCHEMAS`, `ToolsService`) and `storage.py`. These implement the current typed action boundary. `twin.py` is a retained introductory comparison: its legacy `record_contact` and `run_tools` do **not** supply the durable call-ID guarantees taught here.

The SDK answering agent has no write tools. A manually supplied synthetic request is sufficient to practise the registry; do not describe that request as observed autonomous model output. Application-owned explicit consent remains mandatory even if a model proposes an action.

## Practical

From the project directory, inspect the tool schemas and create a private temporary SQLite database. Submit a typed lead, a saved question and an unknown tool using explicit unique call IDs:

```python
from pathlib import Path
from tempfile import TemporaryDirectory
from tools import ToolsService, ToolCall

with TemporaryDirectory() as directory:
    with ToolsService(str(Path(directory) / 'practice.sqlite')) as service:
        calls = [
            ToolCall('record_lead', {
                'name': 'Fictional Visitor',
                'email': 'visitor@example.invalid',
                'message': 'Please discuss the fictional library project.',
                'consent': True,
                'opportunity': 'Synthetic reporting demonstration',
            }, 'lesson06-lead-1'),
            ToolCall('capture_question', {
                'question': 'How were invalid library records tested?',
                'consent': True,
            }, 'lesson06-question-1'),
            ToolCall('shell', {}, 'lesson06-refused-1'),
        ]
        outcomes = service.run(calls)
        print(outcomes)
```

Try missing fields, an invalid email and integer `1` instead of literal `True` consent. Inspect that rejected calls create neither a personal record nor an outbox entry. Compare runtime dataclass checks with `TOOL_SCHEMAS`: a schema declaration never substitutes for application validation or consent.

## Acceptance and evidence limits

The two permitted calls return ordered `ok` outcomes with stable local IDs; the unknown tool is rejected. Record, call fingerprint and structured JSON outbox are committed atomically. No operation sends a message merely by storing a lead/question. The central `test_stage05_semantic_repairs_tools.py` suite contains actual local evidence for these boundaries; retain the exact output from any new demonstration. SDK schema construction is not proof of observed model-origin tool calls.
