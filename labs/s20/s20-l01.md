# s20-l01: Design the Browser Task Sidekick

Define the task lifecycle, architecture, tools, state, safety boundaries and user experience.

## Coherent practical case

An Academy-owned local workshop/catalog research task, with synthetic draft-form interactions only. Keep planning, browser observations, source-attributed findings, evaluation, approvals, artifacts and user-facing progress in one persisted session.

## Source map

Project root: `projects/06-browser-sidekick`. Baseline source anchors: `advanced.py: Plan, SessionController; sidekick.py: TaskStore`. Read the current integrated module listed in the stage workbook as well; baseline helpers alone do not prove full application integration.

## Exercise

Draw the task lifecycle and ownership boundaries. Trace one request from objective through persisted plan, browser tools, evaluator and final workspace.

## Acceptance and reasoning

Distinguish trusted user objective/application policy from untrusted page content. Show persisted task/step IDs, completion evidence, resource limits and approval boundaries. The architecture must include the integrated planner/evaluator/UI rather than treating disconnected helper functions as the finished application.

## Verify your result

Record the command, dependency versions and actual result when you run this exercise. Expected results are not observations. Offline fixtures, SDK construction, model responses, browser interactions and Docker execution verify different things; report skips and failures honestly.

## Integrated application source

Read `projects/06-browser-sidekick/pipeline.py` → `SidekickApplication; NativePlanner; FixturePlanner; PlaywrightSandboxExecutor; Workspace` (references prefixed advanced or ui_gradio name their neighboring module).

One SidekickApplication owns the persisted planner receipts, current run state, step bindings, observations, evaluation and owned artifacts. The UI must use this integrated application rather than bypassing it for disconnected controller calls.

The integration source is a starting point. Verify the configured model, specialists, browser and interface separately; their presence in source is not a successful runtime result.
