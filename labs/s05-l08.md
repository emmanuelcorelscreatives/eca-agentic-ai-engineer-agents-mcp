# s05-l08: Add Contact and Notification Capabilities

Capture opportunity details and notify the agent owner through a configurable notification adapter.

## Authoritative implementation

Use `ToolsService.record_lead`, `pending_outbox` and `dispatch_once` in `projects/01-digital-twin/tools.py`, with `storage.py` and `notifications.NotificationAdapter`. The current path commits a consented opportunity, stable call receipt and structured local outbox atomically. Dispatch has its own durable outcome and cannot recreate the contact.

`workflow.py/contact_and_notify` is retained only as a legacy comparison. Calling it again can insert another contact; its callback/failure result is not the current durable outbox or replay contract. Do not use it as the main workflow for this lesson.

## Practical

1. Record a fictional opportunity with a stable call ID and explicit consent. Retain its lead/contact ID and outbox ID. Repeating that exact call must return the same receipt.
2. Inspect `pending_outbox()`. Run `dispatch_once(outbox_id)` using the default local adapter. Its `dry_run` receipt proves only a local simulation, not that the owner received a notification.
3. Configure a local `NotificationAdapter` whose callback fails. Inspect the durable `local_failed` receipt; retry that local operation only with explicit `retry_local=True`. Verify the lead count stays unchanged.
4. Inspect the explicitly permitted external-adapter path. An actual delivered claim requires an actual `delivered` result and provider/sink receipt ID. A failed, missing or crashed external result remains unknown/dispatching and must not be automatically replayed.
5. Before demonstrating **owner notification**, configure a concrete authorized course-only notification sink/adapter and retain the actual receipt/observation. The curriculum does not require a particular email provider or real customer data; an appropriate truthful course-only sink is acceptable.

## Acceptance and honest status

The actual local tests establish consent, opportunity storage, outbox configuration, local callback/dry-run/failure handling and dedupe. They do not establish delivery to an owner. Existing genuine UI outbox records are queued/pending. Therefore a lesson may describe the implemented adapter and its verified local mechanics now, but must retain the real-run requirement before saying “the owner was notified.” Use `tests/test_stage05_semantic_repairs_tools.py`; do not turn a fixture callback or pending record into a delivered observation.
