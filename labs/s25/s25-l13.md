# s25-l13: Validate Generated Projects Inside Docker

Build and execute generated applications within an isolated environment.

## Coherent practical case

A typed Academy catalog-research/draft-notification agent specification. Generated requirements, architecture, tools, instructions, tests and reviews must feed the same approved dependency graph and produce a real runnable selected-framework project.

## Source map

Project root: `projects/07-agent-factory`. Baseline source anchors: `docker_validate.py`. Read the current integrated module listed in the stage workbook as well; baseline helpers alone do not prove full application integration.

## Exercise

Build and execute the approved generated project using the actual authorized Docker validator and retain container/build/test evidence.

## Acceptance and reasoning

A Docker command plan, permission check or mocked subprocess is not Docker execution. Use the validator declared isolation/resource/network policy, owned cleanup and a verified image/build context. Retain image identity, generated artifact digests, actual exit code and logs. Report unavailable daemon/image honestly; do not relabel the lesson complete.

## Verify your result

Record the command, dependency versions and actual result when you run this exercise. Expected results are not observations. Offline fixtures, SDK construction, model responses, browser interactions and Docker execution verify different things; report skips and failures honestly.

sandbox_validate is the trusted Docker execution boundary. verify_sandbox_receipt must independently authenticate the executor and fresh workspace/image/immutable-suite identity; a matching JSON SHA alone is not authentication.
