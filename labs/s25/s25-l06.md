## Acceptance and reasoning

Declared schemas and limits survive generation exactly. A placeholder must say it is unavailable; it cannot fabricate external success. Review proposed tool code before sandbox execution. Arbitrary unsupported tools must be rejected rather than silently mapped to catalog_lookup or draft_notification.

## Generate the declared catalog/draft tools

Use the same `templates/catalog_research-spec.json` and approved requirements/architecture from Lesson 3. The tools specialist in `Pipeline.generate` must propose source implementing the exact `catalog_lookup` and `draft_notification` IO contracts; `word_count`, `uppercase` and the legacy `text_helper` example are outside this practical's declared capabilities. The catalog is synthetic local data. Draft notification returns text plus `delivered: false`; it does not send mail or create an external message.

Treat proposed modules as untrusted source. Preserve them in the fresh artifact graph and inspect argument checks, result shapes and failure handling. The central owner uses `CentralDockerOwner.validate` and `.verify` as `run_factory` callbacks: both generated tests and the separately supplied immutable `acceptance/` suite execute in actual bounded containers before release. A placeholder integration must report `integration_not_configured` or raise a documented explicit failure; never manufacture an external success receipt.
