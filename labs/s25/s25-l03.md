# s25-l03: Build the Requirements Analysis Agent

Transform the specification into functional requirements, constraints and measurable acceptance criteria.

## Coherent practical case

A typed Academy catalog-research/draft-notification agent specification. Generated requirements, architecture, tools, instructions, tests and reviews must feed the same approved dependency graph and produce a real runnable selected-framework project.

## Source map

Project root: `projects/07-agent-factory`. Baseline source anchors: `advanced.py: requirements; autogen_adapter.py: proposal roles`. Read the current integrated module listed in the stage workbook as well; baseline helpers alone do not prove full application integration.

## Exercise

Ask the requirements model stage to turn the approved spec into functional requirements, constraints and measurable acceptance criteria, then validate its typed output.

## Acceptance and reasoning

The actual structured model result must feed downstream planning after validation/approval. A deterministic mapping can check expected invariants, but it is not the named requirements analysis agent. Reject invented supplied data, contradictory policies, missing spec requirements and unmeasurable acceptance prose.

## Verify your result

Record the command, dependency versions and actual result when you run this exercise. Expected results are not observations. Offline fixtures, SDK construction, model responses, browser interactions and Docker execution verify different things; report skips and failures honestly.

## Current generative implementation

Read `projects/07-agent-factory/` → `model_pipeline.py: Pipeline.analyze, validate_requirements; model_schemas.py: RequirementsProposal`.

AutoGenBackend uses a real AssistantAgent with output_content_type set to the stage schema. Its configured client may submit an actual request only with an explicitly configured account and budget. Pipeline.analyze validates the result against the original approved spec.

Optional generative paths require their SDK dependencies and an explicitly budgeted model account. Fixture tests do not verify model quality, Docker execution or a launched application.

## Exact current catalog specification

Use `templates/catalog_research-spec.json` with `TypedSpec.parse(...)`. Its declared tools are `catalog_lookup(query: string) → {matches: array}` and `draft_notification(recipient: string, body: string) → {draft: string, delivered: boolean}`. The dataset is the synthetic Academy `catalog.json`; required policy includes `no_external_delivery`. Do not use the earlier `text_helper`, `word_count` or `uppercase` demonstration as this project's requirements case.

The genuine requirements specialist receives the entire spec and its SHA. Its `RequirementsProposal` must map purpose, users, datasets, expected output, policies, deployment, framework and every declared tool to IDs and measurable acceptance tests. Preserve unresolved questions and stop planning until they are answered. Approve the exact proposal hash before the architecture specialist receives it. A `REQ-TOOL-*` criterion should require malformed lookup requests to be rejected and draft notifications to produce no delivery side effect, rather than merely require that a function exists.
