## One consistent typed contact contract

For this exercise use **`CONTACT_TOOL` + `CONTACT_RESULT_SCHEMA` + `ContactResult`** in `stage04_selection.py` instead of mixing a stock input with an unvalidated contact output. The only input is a fictional email. `dispatch_contact` validates exact fields and routes against separate application-owned `RequestState` **before invoking** the backend. A model argument such as consent=true cannot grant permission. The included backend stores only synthetic contacts in memory and deduplicates repeated emails.

A successful result must have exact fields status=captured, contact_id matching the declared stable ID format, the **same** email, storage=memory and synthetic=true with correct types. `validate_contact_result` checks returned values; a schema declaration alone is not validation. Inject missing/extra fields, wrong booleans/email/storage/ID and a backend exception. Errors are fixed sanitized structures; no arbitrary backend text is shown.

An invalid return can follow an actual backend effect. The result explicitly says UNKNOWN_DO_NOT_RETRY and requires human inspection; no rollback or safe paid replay is promised. Invalid input/consent returns NOT_INVOKED and the backend must never run. This is a deterministic contract lab, so no provider call is needed to prove these boundaries.
